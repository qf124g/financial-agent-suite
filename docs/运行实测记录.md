## 一、反应式 Agent（reactive_fund_qa）实测

### 测试输入

```
私募基金合格投资者需要满足什么条件？
```

### 实测 trace：三轮自主推理

```
第1轮：模型调用 answer_question
       → 知识库无直接匹配，工具返回"未找到相关信息"

第2轮：模型自主改变策略，并行调用两个工具：
       search_rules_by_keywords("合格投资者")
       search_rules_by_category("设立与募集")
       → 两个工具均命中知识库规则

第3轮：综合两个工具结果，输出最终答案
       （合格投资者标准、100万门槛、单位/个人条件）
```

### 关键观察

1. **失败后自主换策略**：第一次检索未命中，模型没有放弃、也没有编造答案，而是自主决定改用关键词搜索 + 类别搜索双路并行重试——这是 ReAct 架构"边想边做"的真实体现
2. **并行工具调用**：第 2 轮一次发出两个 tool_calls，模型自己判断两个检索手段互补，无需人工编排
3. **token 累积可见**：prompt_tokens 逐轮增长（574 → 644 → 935），直观展示上下文累积机制；第 1 轮 reasoning_tokens=93，说明模型在第 1 轮做了较多内部推理
4. **协议完整**：trace 中可见 AIMessage(tool_calls) → ToolMessage(tool_call_id 对应) → AIMessage 的标准消息序列

## 三、实测发现的问题：答非所问 bug

### 现象

用户查询是**子女教育金 10 年计划**，但深思熟虑链输出的报告通篇围绕**退休规划**（550 万缺口、15 年退休目标、退休支出）。

### 原因分析

- 客户画像（模拟财务数据）中包含"退休规划"财务目标
- 推荐生成 prompt（RECOMMENDATION_PROMPT）中，客户画像信息权重过高，压过了用户查询本身
- 模型被画像中的财务目标带偏，围绕画像生成而非围绕用户问题生成

### 修复方案

在 RECOMMENDATION_PROMPT 中增加硬约束：

```
建议内容必须紧扣用户查询本身，客户画像仅作背景参考，
不得将画像中的财务目标当作用户本次的需求。
```

### 价值（重要）

这个实测发现的问题：

1. **效果评估（DeepEval）**：
   "我的投顾 Agent 实测中被 AnswerRelevancy 指标抓到过答非所问——用户问教育金，模型答退休，因为 prompt 里客户画像权重过高压过了用户问题本身。这正是需要自动化评估体系的原因：这种问题人工抽查很难稳定发现。"

2. **防幻觉/可控性**：
   "这就是为什么我在 RAG 项目里坚持引用溯源——没有引用锚定的生成，模型跑偏了都难以察觉。评估指标 + 引用溯源是互补的两道防线。"

## 七、DeepEval 效果评估（evaluation）实测

### 测试方式

跑 1 个反应式用例（"今天上证指数表现如何？"），用三个指标端到端评估。

### 实测评估结果（真实分数）

| 指标 | 分数 | 阈值 | 结果 | 评判理由（摘要） |
|---|---|---|---|---|
| AnswerRelevancy（相关性） | 0.500 | 0.6 | **FAIL** | 回答包含上证指数相关有效信息，但被无关内容稀释——Agent 多做了一段 AI 自我介绍，偏离了问题本身 |
| Hallucination（幻觉） | 1.000 | 0.5 | **PASS** | 输出与上下文完全一致，点位/涨跌/涨跌幅均准确，无编造矛盾信息 |
| GEval（风险偏好考虑） | 0.000 | 0.5 | **FAIL** | 回答是通用行情播报，未涉及任何风险相关内容，也未结合客户风险等级给出个性化建议 |

### 实测发现的 DeepEval 工程坑（修复要点）

1. **评判器连不上（Connection error）**：只传 `model="qwen3.7-plus"` 字符串，DeepEval 默认连 OpenAI 官方 api.openai.com，而非自定义端点。**解法**：显式构造 `OpenAIModel(model, api_key, base_url)` 指向兼容端点。
2. **`evaluate() got an unexpected keyword argument 'print_results'`**：DeepEval 4.x 把 `print_results` 从 `evaluate()` 参数移入 `display_config`。**解法**：移除该参数（4.x 默认即打印结果）。
3. **HallucinationMetric 报 `'context' cannot be None`**：幻觉检测用的是 `LLMTestCase.context`（事实依据），不是 `retrieval_context`。**解法**：构建用例时同时传 `context`。

### 评估结果（极重要）

这组真实分数是讲 DeepEval 的**活教材**：

- **相关性 FAIL（0.5）暴露了真问题**：Agent 在回答前多做了一段自我介绍，被 AnswerRelevancy 精准扣到阈值之下——证明评估指标不是摆设，能抓到人工难察觉的"答非所问/冗余"
- **幻觉 PASS（1.0）证明溯源有效**：行情数据与上下文完全一致，说明工具结果强制回注 + 上下文约束确实压住了幻觉
- **GEval FAIL（0.0）暴露指标设计问题**：用"风险偏好"指标去评一个纯行情播报的查询本身就不匹配——这反过来印证了"评估指标要和查询类型对齐"这个工程判断

这套"指标抓到真问题 + 指标设计本身需校准"的双向认知，远比背三个指标名更能体现评估体系的实战深度。

## 八、高德地图 Agent（assistant_mcp_amap_bot.py）启动笔记

> 已于 2026-11-06 实测跑通，Web 界面地址 http://localhost:7860

### 启动命令（完整）

```bash
cd mcp_tools
export PATH="/Users/test/.nvm/versions/node/v20.20.2/bin:$PATH"   # Node 20+ 在前排
export npm_config_cache=/tmp/npm-cache                              # 绕过 ~/.npm 的 root 残留缓存
export OPENAI_API_KEY="$DASHSCOPE_API_KEY"                          # 大模型 key
export AMAP_API_KEY="你的高德key"                                    # 高德开放平台 Web服务 key
/usr/local/bin/python3 assistant_mcp_amap_bot.py
```

启动成功标志：日志出现 `Amap Maps MCP Server running on stdio` + Gradio 监听 7860 端口。

### 前置依赖

| 依赖 | 说明 | 获取方式 |
|---|---|---|
| Node.js 20+ | 高德 MCP Server 是 npm 包 `@amap/amap-maps-mcp-server`，通过 npx 启动 | `nvm` 或 `brew install node` |
| 高德 API Key | 调高德开放平台接口用，免费 | lbs.amap.com → 控制台 → 创建应用 → 添加 Key（**服务平台选"Web服务"**） |
| npm 缓存正常 | 本机 `~/.npm` 有 root 残留会导致 EACCES | 永久修复：`sudo chown -R 502:20 ~/.npm` |

### 关键坑：MCP 子进程 env 是"替换"不是"合并"

实测发现：MCP SDK 的 `stdio_client` 中，一旦在配置里传了 `env` 字典，**子进程环境会被完全替换**，不再继承父进程的 PATH 等变量——直接导致 npx 走默认缓存报 EACCES。

修复（assistant_mcp_amap_bot.py 已改）：

```python
mcp_env = dict(os.environ)          # 先拷贝父进程完整环境
mcp_env["AMAP_MAPS_API_KEY"] = ...  # 再注入业务变量
```

这个"替换而非合并"的行为差异是 MCP 接入第三方 Server 时的高频坑

### 验证过的能力

地理编码、路线规划（如"浦东机场到外滩"）、周边搜索（如"南京路附近本帮菜"）、行程规划，模型自动编排多个高德工具完成复合任务。

## 九、LangSmith 追踪与批量评估（evaluation/langsmith_evaluation.py）

### 能力构成

| 能力 | 实现 | 说明 |
|---|---|---|
| Trace 追踪 | 环境变量开关，零代码改动 | `LANGSMITH_TRACING=true` 后，三个 Agent 的 LLM 调用/工具调用/图节点流转自动上报 |
| 数据集管理 | `create_test_dataset()` | 4 条用例（2 反应式 + 2 深思熟虑），含期望路由模式和期望关键词 |
| 路由正确性评估 | `processing_mode_evaluator` | 混合式架构核心指标：简单查询是否走反应式、复杂查询是否走深思熟虑 |
| 回答完整性评估 | `keyword_completeness_evaluator` | 期望关键词覆盖率（如"教育金"问题回答须含"教育金""建议"） |
| 批量执行 | `evaluate(max_concurrency=1)` | 串行跑测试集防限流，结果自动上报 LangSmith 网页可对比 |

### 运行方式

```bash
export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY="smith.langchain.com 注册的 key"
export OPENAI_API_KEY="$DASHSCOPE_API_KEY"
python evaluation/langsmith_evaluation.py
```

### 迁移时的两处适配（相对课程版）

1. 被测对象：课程版 `ChatTongyi` → 套件版 OpenAI 兼容模式（qwen3.7-plus + token-plan 端点）
2. API 简化：课程版用 `RunEvaluator` 类 + 三层防御性输入提取（600 行）；新版 langsmith 0.4 的 `evaluate` 直接把 inputs 传给目标函数，评估器用普通函数即可（精简到约 180 行）

### 评估体系

"评估体系是双层的：DeepEval 做离线指标打分（相关性/幻觉/GEval），LangSmith 做在线 trace 追踪 + 测试集回归。回归的核心指标是协调层路由正确率——混合式架构里路由错了，后面链路再准也白搭。"
